# My Ledge 상품화 준비 심층 검토

작성일: 2026-10-22 · 검토 기준: `9876439ff67f03ebb736b336025e92503ddad940`

## 판단

**현재는 개인 사용자가 운영하며 보정하는 장부 도구로서 기반이 좋지만, 고객이 계산 결과와 데이터 보존을 믿고 비용을 지불할 단계에는 도달하지 않았다.** 대체 거래 승인 시 중복 집계, 부분 환불 잔액 소실을 합성 데이터로 재현했다. 외부 사용자에게 제공하려면 인증·권한 경계도 먼저 바꿔야 한다. 화면을 더 꾸미거나 예측 기능을 늘리기 전에 **금액 보존 → 승인한 내용과 적용 결과의 일치 → 실패 복구 → 접근성·운영 검증**을 고정하는 것이 우선이다.

원본과 사용자 보정의 분리, source provenance, 관측값/추정값 표시, 일부 미리보기 토큰, 삭제·병합 제외, 부분월 설명, 일관된 디자인 시스템은 유지할 자산이다. 전면 재작성보다 이 기반의 경계 조건을 바로잡는 접근을 권한다.

이 문서는 조사·개선 제안이다. 앱 수정, 운영 데이터 복구, 배포 완료를 의미하지 않는다. 기존 T 항목의 완료 이력을 지우지 않고 이번 발견을 후속 작업으로 연결했다.

## 범위와 증거 수준

- **동기화:** 원격 fetch 후 로컬 main과 origin/main의 차이는 0/0이었다. 문서 브랜치는 최신 origin/main에서 만들었으며 기존 미추적 파일은 보존했다.
- **소스 검토:** 금융 처리 흐름, API·모델·migration·CI·Docker 설정과 프론트엔드 13개 route를 세 영역으로 병렬 검토했다. 통합 검토에서 주요 경로와 합성 재현을 다시 확인했다.
- **실행 재현:** 실제 backend 서비스 함수를 인메모리 SQLite에 연결해 아래 금융 사례를 재현했다. 운영 금융값을 재현 fixture로 사용하지 않았다. FE-01/02/03/05도 실제 컴포넌트에 지연·오류·입력 상태를 주입한 임시 테스트 4개로 재현하고 통합 검토에서 재실행했다.
- **브라우저:** 데스크톱 1440×900에서 13개 route 전체, 거래 상세와 대출·할부·규칙 하위 탭을 직접 확인했다. 브라우저 담당의 독립 검토를 코드·DOM 확인과 교차했다. 화면별 범위는 [Live 상세](live-review.md)에 기록했다.
- **배포와 소스의 연결:** frontend `/build-info.json`은 `d9f10c2`와 JSON/no-store를 반환했다. 이 커밋부터 검토 기준까지 backend/frontend 코드 차이는 없다. 배포 backend의 Python 소스 100개를 로컬과 hash 대조해 전부 일치했다. 이것이 의존성·환경설정까지 동일하다는 뜻은 아니다.
- **운영 관찰:** API health 성공과 별도로 읽기 전용 DB 트랜잭션에서 유효 거래 존재 및 migration `20260924_0032`를 확인했다. 인증 헤더 없는 거래 GET은 200, canonical dashboard GET은 401이었다. 따라서 “모든 조회가 공개”가 아니라 조회 경계가 endpoint별로 다르다.
- **경계:** 운영 upload/apply/reset 및 장애 주입은 실행하지 않았다. 실제 모바일 viewport 변경 기능이 제공되지 않아 모바일 겹침은 구조 위험으로만 기록했다. 부하·백업 복원·다중 사용자 격리는 실행 검증한 성능/안전 보증이 아니며 아래 출시 gate에 명시했다. 운영 주소, 개인 금융값, 비밀, 원본 화면 캡처는 이 문서 묶음에 포함하지 않았다.

표의 **실행**은 합성 실행 결과, **코드**는 분기·계약 추적, **화면**은 실제 브라우저 관찰, **설계**는 제품 모델이나 정책을 결정해야 하는 공백이다. 모든 개선을 같은 종류의 버그로 취급하지 않는다.

## Live에서 우선 조치할 사항

실제 화면·DB 대조에서 **진행월 저축률 대표값의 T023 계약 회귀(L01)**를 확인했다. 수입이 아직 적게 수집된 상태의 과도한 음수 비율이 데이터 사전 대표 카드에 표시된다. 원본 비율과 대표값의 충분성 판정을 분리해 T045에서 고친다.

인박스 2,143행 중 89.2%는 반복 성격만 미지정인데 화면은 일반적인 미분류 큐로 보인다. 동시에 표시되는 100%는 이번 달 일부 지출액의 필요도 분류율을 반올림한 것이며, 전체 큐 완료율이 아니다(L02). 선택된 오래된 투자 소스(L03), 순자산 교체 범위 미완성(L04), 대출 유형·추정 전제 검토(L05), 최근 10건 밖의 과거 부분 실패(L06)도 사용자가 다음 조치를 찾을 수 있게 해야 한다. 출처 누락·lineage 공백(L07)과 환불 후보(L08)는 원본 검토 없이 자동 복구할 대상이 아니다.

반대로 현재 DB의 superseded·비KRW·settlement match는 모두 0이다. F01/F02/F04가 현재 운영 금액을 이미 오염시켰다는 증거는 없다. 초기화는 실제 FK·연결 데이터가 있어 F08의 위험 전제가 존재하지만 운영 reset으로 실패를 유발하지 않았다. [전체 관측·완료 기준·SQL](live-review.md)

마지막 사례는 FK를 켠 SQLite 재현이다. PostgreSQL에서 실제 reset을 실행한 증거와 혼동하면 안 된다. 위 표는 오류 발생률이나 운영 장부가 이미 오염되었다는 통계가 아니다. 수정 시 영향받은 기존 데이터의 탐지·복구 계획까지 별도로 정의해야 한다.

## 상품 UX의 목표 구조

### 1. 첫 사용자는 “파일을 넣고 맞는지 확인”까지 스스로 완주해야 한다

지금 가져오기 화면은 파일·기준일·미리보기라는 기본 흐름을 제공하지만, BankSalad에서 어떤 파일을 받는지, 거래 기간과 스냅샷 기준일이 왜 다른지, 없는 섹션이 무엇을 뜻하는지 설명이 부족하다. 실제 화면에는 업로드 상태 `success`가 그대로 나온다. 초기화 영역은 일상 업로드와 같은 페이지에 있어 비정상 복구의 기본 선택으로 오해할 여지도 있다.

권장 흐름은 **파일 준비 안내 → 파일·형식·기준일 확인 → 거래와 스냅샷 영향 미리보기 → 선택 승인 → 적용 결과와 미해결 항목**이다. preview에는 신규/수정/대체/삭제뿐 아니라 기준일, 통화, 섹션 수집 범위, 사용자 보정 보존 여부를 보여준다. 성공 후에는 적용 batch와 이전 값에 접근할 수 있어야 한다. 날짜를 자동 추출하지 못하면 이전 파일의 날짜를 조용히 물려주지 않는다. 초기화는 별도 고급 데이터 관리 영역으로 낮춘다.

### 2. 홈은 “현재 상태 → 해야 할 일 → 근거” 순서로 읽혀야 한다

실제 데스크톱 홈에서 낮은 신뢰도의 월말 전망이 가장 크게 나오고, 자세한 전망 근거가 긴 영역을 차지한 뒤 데이터 품질 작업이 나온다. 관측·추정 라벨은 이미 좋은 기반이다. 여기에 최신 업로드와 관측 종료일, 부족한 데이터, 해결 가능한 작업을 앞쪽에 모아 사용자가 다음 행동을 찾게 한다.

- 첫 영역: 관측 기준일과 최신성 → 관측 순현금흐름·순자산 → 전망은 신뢰도·범위와 함께 표시.
- 다음 영역: 영향이 큰 확인 작업 3개, 이유와 해결 화면으로 이동. 수천 건 전체 큐를 첫 행동으로 제시하지 않는다.
- 상세 영역: 수입·지출 전망 근거, 전체 가정, 데이터 출처. 접어서 읽을 수 있게 한다.

분류 커버리지 100%와 대규모 품질 검토 큐가 동시에 존재할 수 있다. 계산 오류로 단정할 일이 아니라 서로 다른 지표다. **“분류 값이 있음”과 “사용자가 검토 완료함”을 다른 이름·분모·설명으로 표시**해야 신뢰를 잃지 않는다. 이 재배치는 사용자 평가로 검증할 UX 가설이며, 클릭률 개선을 이미 측정한 결과가 아니다.

### 3. 일상 사용과 전문가 설정의 밀도를 나눈다

설정 화면에서 `median_30pct_exclusion`, `prorated_closed_month_baseline`이 자유입력란에 보였다. 사용자가 내부 알고리즘 식별자를 알아야 설정할 수 있는 구조는 소비자 제품에 맞지 않는다. 기본 설정은 한국어 선택지와 결과 예시로 제공하고, 전문가 파라미터는 접힌 고급 영역에 둔다. 고정된 알고리즘은 편집 가능한 입력보다 읽기 전용 설명이 적절할 수 있다.

거래 화면의 밀도는 운영 작업에 적합하므로 단순히 모든 표를 카드로 바꾸지 않는다. 대신 다음을 보장한다.

| 핵심 여정 | 목표 경험 | 완료를 확인할 방법 |
|---|---|---|
| 거래 검색·수정 | 명시적 편집 버튼, 변경 표시, 저장/버리기, 조회 맥락 복원 | 키보드로 열기·수정·저장·복귀; 뒤로가기 후 필터 유지 |
| 대량 분류·규칙 | 선택된 전체 범위와 화면 밖 개수, before/after, 승인 당시 대상 고정 | 필터 변경·재조회·동시 수정 후에도 숨은 ID가 적용되지 않음 |
| 삭제·복원 | 삭제 성공과 복원 성공을 구분, 실패 시 액션 유지 | 복원 500/offline을 주입해 사용자에게 실패와 재시도 표시 |
| 모바일 편집 | 상세 패널과 하단탭 분리, 가상키보드·safe area에서도 CTA 노출 | 320/390/768px 실제 렌더와 입력·scroll·저장 버튼 접근 |
| 읽기 권한 사용자 | 수정 불가 이유와 필요한 권한을 화면 크기와 무관하게 안내 | desktop/mobile capability 표시와 실제 API 권한 일치 |

키보드 조작과 합리적인 focus 이동은 외관 선호와 별개의 기본 접근성 기준이다. 거래 편집 진입과 dialog의 focus 경계를 먼저 고친다. [W3C WCAG 2.2 Focus Order](https://www.w3.org/WAI/WCAG22/Understanding/focus-order.html)

## 상품 모델별 출시 조건

| 모델 | 현재 구조와의 거리 | 반드시 필요한 조건 |
|---|---|---|
| 개인 사설망 도구 | 현재 의도에 가장 가까움 | F01/F02 등 정확성, 수집 보존, 복구 계약, 사용성 결함 해소 |
| 고객별 독립 인스턴스 상품 | 단일 장부 모델을 유지할 수 있음 | 고객별 DB/volume/credential 격리, 인증 프록시·TLS·우회 차단, 안전한 설치/업데이트/백업 |
| 공용 다중 사용자 서비스 | 데이터 모델 변경 필요 | 사용자 identity, tenant 범위의 FK/unique/query/source/파일 저장, 권한·agent token 분리, 교차 접근 테스트 |

권장 출발점은 고객별 독립 인스턴스 또는 소수의 통제된 단일 사용자 베타다. 공용 서비스를 선택한다면 로그인 화면 추가로는 부족하다. 제품 모델이 결정되기 전 tenant schema나 과금 기능부터 만들지 않는다. T022의 장기 확장 중 백업·배포 안전은 현재 단계의 필수 조건으로 분리하고, 예산·코칭·90일 예측은 계산 신뢰 이후에 이어간다.

## 실행 순서와 완료 gate

| 단계 | 작업 | 완료 조건 |
|---|---|---|
| 1. 금액 신뢰 | T045 + T049의 PostgreSQL 테스트 기반 | 대체/환불/삭제/병합/통화의 불변식, 월 현금흐름 basis, API–SQL view parity 통과 |
| 2. 수집·조작 신뢰 | T046 + T047 | 같은 파일 재실행, 새 날짜, 섹션 누락, 늦은 preview, 선택 범위, 오류·복원에 대한 회귀 검증 |
| 3. 첫 사용·일상 UX | T048 | 업로드→대조→수정→복원 핵심 여정을 신규 사용자·키보드·모바일로 완주 |
| 4. 판매 가능한 운영 | T049 + T050 + T051 | 배포 경계, 복구 drill, readiness, 자원 제한, 민감 로그 차단, 선택한 제품 모델의 격리 검증 |

T050의 제품 모델 결정과 T051의 복구 설계는 1단계와 병행할 수 있다. 공용 노출은 해당 gate를 통과한 뒤 한다. T035/T036 반복계약과 T037 예측 고도화는 기존 범위를 유지하되 입력·분류·통화 계약을 먼저 안정화한다. 일정은 인력과 모델 결정에 따라 정하며 근거 없는 주 단위 완료 약속을 붙이지 않는다.

출시 gate는 “테스트 수가 많음”이 아니라 다음 실패를 잡는지로 평가한다.

1. **금액 보존:** 부분 환불 배분 전후 전체 순액 동일, 대체 lineage당 유효 금액 1회, 삭제/병합 제외, 통화별 단위 보존.
2. **승인 보존:** preview의 파일·날짜·대상·기준 revision과 apply가 일치. stale preview는 재검토 요구. timeout은 처리결과 확인 후 재시도.
3. **원본·사용자 보정 보존:** optional 누락/명시적 빈 값/삭제를 구분하고 재업로드 뒤 override와 출처를 설명할 수 있음.
4. **운영 DB 검증:** PostgreSQL fresh upgrade, 대표 과거 revision upgrade, FK/lock/concurrent apply/reset rollback, canonical SQL 결과 대조.
5. **복구:** 별도 환경에 DB와 원본을 복원하고 사용자 메모·분류·연결·source lineage까지 비교. RPO/RTO 목표를 먼저 승인하고 실측.
6. **사용성:** offline/401/409/422/500이 empty나 0으로 위장되지 않음. 실제 mobile/keyboard 여정 통과, 저장 결과를 readback.
7. **규모:** synthetic 1만행 preview와 장기간 장부를 대상으로 렌더·상호작용·API p95·메모리 예산을 측정. 예시 목표인 첫 review 2초/선택 반응 200ms는 대상 기기·네트워크를 정한 뒤 확정할 제안값이다.

## 보존할 판단과 후속 승인 경계

완료된 T030/T031/T032/T042/T043의 구현·역사는 유지한다. 이번 감사는 그 조합과 경계에서 발견한 회귀/계약 공백을 추가한다. T020 이체 추적의 보류, T035–T039 등 기존 백로그도 임의로 완료 처리하거나 대체하지 않는다.

후속 구현 후보 T045–T051은 범위·guardrail·완료 기준이 준비된 **계획됨, 구현 승인 전** 상태다. 다음 결정은 우선 T045의 금액 신뢰 복구 범위와 T050의 상품 제공 모델이다. 이 문서를 승인하는 것과 운영 데이터 수정·배포·PR 병합을 승인하는 것은 별개다.
